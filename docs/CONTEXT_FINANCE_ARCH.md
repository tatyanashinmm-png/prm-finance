## Что это и зачем

Переписываем финансовый дашборд с самодельного монолита (HTML-строка внутри Worker'а)
на промышленный стек. Цель: (1) убрать класс багов с генерацией кода в строке;
(2) вынести финансовую методологию в тестируемое ядро; (3) сделать приложение
источником правды вместо Google-таблицы; (4) вход и роли; (5) PWA; (6) автодеплой.

Владелец — Татьяна. Не программист: нужны пошаговые действия и готовые файлы, правки
через веб-интерфейс GitHub, git/терминал — через Claude Code.

## Схема данных (нормализованная; периоды СТРОКАМИ, не столбцами)

Ключевой принцип: не зеркалить широкую таблицу (~128 колонок -> упёрлись бы в лимит
D1 в 100 колонок). Периоды — строки.

- **contracts**: id (PK), contract_num (уникальный натуральный ключ), client_name,
  legal_entity, status («Активен»/«Блок»), manager, note, updated_at.
- **periods**: id (PK), period_start (дата 1-го числа месяца, уникальна).
- **invoices**: id (PK), contract_id (FK), period_id (FK), invoice_amount,
  paid_status (СЫРОЙ текст «Да»/«Нет»/пусто), updated_at; уникальность (contract_id, period_id).
  Поля invoice_number НЕТ (выяснили: столбец «Счет» в таблице — boolean true/false
  «счёт выставлен», а не номер; для метрик не нужен, удалён).
- **tariffs**: id (PK), contract_id (FK), tariff (месячная абонплата), effective_from;
  натуральный ключ (contract_id, effective_from). ЗАДЕЛ ПОД ИСТОРИЮ: сейчас 1 запись
  на контракт (tariff = колонка H, effective_from = самый ранний период контракта),
  но структура позволяет тарифу меняться помесячно — заполнится, когда пойдёт история
  из хука биллинга. Сущность «подписка» НЕ заводим (сейчас 1 контракт = 1 подписка = 1 тариф).
- **users**, **sessions** — для входа (см. выше).

Миграции: 0001–0003 (базовые + drop invoice_number), 0004_add_tariffs. Применены и
локально, и на remote.

## Методология метрик (ЗАКРЫТА под золотыми тестами)

Принцип проекта: сначала эталон из таблицы, потом код; совпадение до рубля; расхождения
допустимы ТОЛЬКО там, где доказано, что таблица неправа. Чистое ядро без БД/Cloudflare:
`worker/core/{mrr,arpu,movement}.mjs`. Эталон — `golden-mrr.json`, тесты — `scripts/*golden*`.

### Базовый слой (шаг 5.1) — mrr.mjs
- MRR = сумма invoice_amount где paid_status="Да" (по СУММЕ ОПЛАЧЕННОГО СЧЁТА),
  без фильтра по текущему статусу контракта.
- issued_count = число invoices в периоде; paid_count = оплаченных; issued_amount = сумма всех.
- Расшифровка нижней строки таблицы под месяцем: 1-е число = сумма выставленных;
  дробь = выставлено/оплачено (шт); 3-е число = сумма оплаченных = MRR.
- Эталон MRR май–авг 2026: 2 060 986 / 2 016 385 / 1 826 328 / 1 936 140.
- Результат: счётчики совпали везде; MRR — где расхождение, оно РОВНО равно ячейкам,
  где сумма записана ТЕКСТОМ (родная СУММЕСЛИ считает текст как 0, наш toNum — верно;
  МЫ ТОЧНЕЕ). Известные текстовые ячейки: "12 809" Truck-Price май, "15 326" Премиум
  Эстетикс июнь, "2812.90" РЕКЛАМНЫЙ СТИЛЬ авг.

### ARPU (шаг 5.2) — arpu.mjs
- ARPU = среднее ТАРИФА (колонка H, не суммы счёта!), действовавшего на дату периода
  (последняя запись tariffs с effective_from <= period_start), среди контрактов с
  paid_status="Да". Пустые тарифы в среднее не включаются.
- БАГ В ТАБЛИЦЕ: формула AVERAGEIF(условие со строки 12; $H:$H со строки 1) даёт
  СДВИГ тарифа на 11 строк (тариф берётся у чужого контракта) — 105 из 120 оплативших
  в мае получали чужой тариф. Наш расчёт правильный (тариф того же контракта по ключу).
- РЕШЕНИЕ: считаем нашим правильным расчётом; расхождение с таблицей принято осознанно.
  В golden: arpuSheet (табличный, помечен source_bug, для истории) + ourArpu (боевой эталон).
- Наш правильный ARPU май–авг 2026: 17 107 / 17 374 / 18 149 / 18 753
  (табличные багованные были 17 681 / 18 099 / 18 122 / 18 375).

### Движение MRR (шаг 5.3) — movement.mjs
- НОВЫЙ (шт): в пред.месяце счёта не было ИЛИ не оплачен, в текущем оплачен.
- ОТТОК (шт): в пред.месяце оплачен, в текущем счёта нет ИЛИ не оплачен.
- Чистый приток = новые − отток (штуки).
- ДЕНЬГИ ПО ТАРИФУ H (не по сумме счёта): New MRR = сумма тарифа ТЕКУЩЕГО месяца по
  новым; Churn MRR = сумма тарифа ПРЕДЫДУЩЕГО месяца по оттоку; monthly change = New−Churn.
- Формулы движения в таблице (COUNTIFS/SUMIFS) — полные столбцы одного размера, СДВИГА
  НЕТ, эталон достоверен (в отличие от ARPU).
- Результат: штуки совпали везде; деньги — кроме тех же текстовых ячеек (BLOCK-Земская
  ЕДА, тариф "43 890,00" росс.формата — май/ноябрь, +-43890, мы точнее).
- Expansion / Contraction / Reactivation — ОТДЕЛЬНЫЙ СЛОЙ ПОЗЖЕ: в текущей методологии
  Татьяны их нет (модель двухкатегорийная New/Churn), станут осмысленны, когда тариф
  начнёт меняться помесячно из хука биллинга. Тогда — как новая аналитика, проверяемая
  через тождество «сумма категорий = monthly change».

Важно: движение сверяем с ДВИЖЕНИЕМ из таблицы, НЕ с разницей базового MRR (базовый
MRR по сумме счёта, движение по тарифу — основания разные).

## ОБНОВЛЕНИЕ — модель клиентов/подписок + уточнённый порядок работ

> Дописано после проработки промышленной модели. Этот раздел уточняет и заменяет
> порядок из «Что дальше» выше. Ключевое: клиенты/подписки — СЛЕДУЮЩИЙ шаг;
> платежи/хуки — В САМОМ КОНЦЕ отдельной подсистемой.

### Решение по модели (принято)

Расщепляем плоскую «контракт» на промышленный перёд хребта **Клиент → Подписка →
Тариф → Счёт**. Сегодня 1 контракт = 1 подписка, поэтому рефакторинг 1:1 и НИ ОДНО
ЧИСЛО не двигается — золотые тесты это доказывают (они и есть страховка рефактора).

- **clients**: name (СЕЙЧАС ключ группировки — нормализовать пробелы/кавычки),
  inn (пусто, БУДУЩИЙ ключ группировки — появится позже, тогда перегруппируем по нему),
  manager, status («Активен»/«Блок»), note, timestamps.
  Группировка по имени ВРЕМЕННАЯ и приближённая: одноимённые разные юрлица
  (напр. «Донуля 2» — ИП Плешаков и Юмобайл) СЕЙЧАС сольются в одну карточку клиента
  и корректно разделятся, когда придёт ИНН. На МЕТРИКИ это не влияет (считаются на
  уровне счёта/подписки, не клиента) — «плывёт» только группировка карточек, обратимо.
- **subscriptions**: client_id (FK), contract_num (натуральный ключ из таблицы,
  РЕДАКТИРУЕМЫЙ — при реактивации номер вписывается вручную), legal_entity
  (пер-контрактное, живёт здесь), status, started_at/ended_at, billing cycle, timestamps.
  Один клиент → НЕСКОЛЬКО подписок во времени. Реактивация = НОВАЯ подписка под тем же
  клиентом со своим (вручную вписанным) номером. Заблокированные без номера →
  BLOCK-<имя> (коллизия → BLOCK-<имя>-<юрлицо>) — как уже сделано.
- **tariffs / invoices** — перенаправить с contract на subscription; история тарифа
  (effective_from) и paid_status (сырой текст) — как есть.

### Уточнённый порядок работ

1. [СДЕЛАНО] **Рефакторинг модели**: clients + subscriptions (1:1, под золотыми тестами —
   доказать, что числа не сдвинулись).
2. [СДЕЛАНО] **Карточка клиента** (сначала только чтение) + вид подписки.
3. **Витрина дашбордов** поверх модели.
4. **ПОТОМ, отдельной подсистемой и отдельным чатом — billing-sync** (платёжная
   синхронизация). НЕ начинать раньше. Свой CONTEXT_BILLING_SYNC.md соберём на этой стадии.

### Billing-sync — дизайн намечен (для будущего отдельного чата, НЕ сейчас)

Опытная эксплуатация: и таблица, и приложение питаются ОДНИМ потоком событий биллинга
(нет двойного ручного ввода), сверка ловит расхождения; переключение — после N чистых
периодов сверки.

- Биллинг умеет 1 адрес → нужен **РЕТРАНСЛЯТОР**: отдельный воркер на СВОЁМ адресе,
  принимает событие и шлёт две копии: (1) в существующий billing-webhook БАЙТ-В-БАЙТ,
  прозрачно (включая заголовок X-Webhook-Token), → таблица как сейчас; (2) в приёмник
  приложения по принципу «отправил и забыл» (если лежит — платёжный путь не страдает).
- Код billing-webhook НЕ трогаем. Переключение биллинга на ретранслятор ОБРАТИМОЕ
  (одна правка адреса в биллинге; откат = вернуть адрес назад = сегодняшнее проверенное
  состояние). Обкатка на тестовом контракте revvy 07.3007-03.24 (у биллинга есть
  тестовый режим).
- События биллинга: создание/удаление платежа; подключение подписки (первый авансовый/
  скидочный счёт); создание/снятие блокировки.
